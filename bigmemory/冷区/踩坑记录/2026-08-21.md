### 共享 RViz 配置会让旧默认 profile 看不到点云

- 现象：静态验收发现，默认 `legacy_planner_v1` 仍发送单云
  `SENSOR_FRAME_V1`；Foxy 解码该帧时只更新规划云发布器
  `/quad_0/cloud`。共享 RViz 与 voxel capture 却已改为只订阅
  `/quad_0/cloud_raw`，因此旧默认模式可能完全无点云显示。本次
  未实际启动 legacy runtime，故运行时现象仍待回归确认。
- 已验证原因：云协议保持向后兼容，但显示 topic 配置被全局切换，
  没有按 profile 分流，也没有 legacy fallback。
- 修复/预防：将 RViz/voxel 订阅 topic 与 cloud profile 绑定，或为
  V1 显式发布 raw fallback；新增一项真实 legacy profile 回归，同时
  断言 topic 有数据且 RViz 来源不为空。
- 证据：`integration/lite3_sim_bridge/lite3_sim_bridge/run_isaac_v12_fallback.py`
  中默认 profile 和双云分支；
  `integration/lite3_sim_bridge/lite3_sim_bridge/foxy_bridge_node.py`；
  `integration/lite3_sim_bridge/config/foxy_native_scan_review.rviz`；
  `integration/lite3_sim_bridge/lite3_sim_bridge/voxel_capture_node.py`。
- 后续意义：新 profile 的点云可见性不能外推为旧默认模式无回归。

### 远端 manifest 不等于完整本地实体归档

- 现象：将远端 manifest 声明的 `130` 个文件与 canonical 本地结果树
  比对，仅 `66` 个匹配，`63` 个本地缺失，且 `closed_loop.mp4`
  的哈希不一致。
- 原因：尚未确定。已确认 revision manifest 同时记录了
  `remote_complete_tree_manifest_sha256` 和不同的
  `local_subset_manifest_sha256`，而实施清单仍将“回收完整 artifact tree
  并证明递归 SHA-256 相等”保持未勾选；不足以进一步推断缺失是
  未传输、被排除还是另有本地副本。
- 修复/预防：保留远端原树，回收到主项目相同相对路径，对
  `130` 条逐条重算 SHA-256；对 `closed_loop.mp4` 单独确认哪个是
  不可变 master，不覆盖任一旧实体。在缺失数和不同数均为零前，
  不得写成“完整本地归档”或“远端/本地 parity 通过”。
- 证据：
  `.pipeline/experiments/2026-08-17_office_l0_scan_crowd/revisions/office-v2.0.1-go2-geometry-preflight.manifest.json`；
  `.trellis/tasks/08-20-v2-0-1-cloud-traversability/implement.md`
  第 115--116 行的未勾选回收门。
- 后续意义：索引、哈希清单和远端成功只是回收线索，不能代替
  本地可打开实体与递归 parity。

### telemetry 建连超时参数未实际用于建连

- 现象：Go2 profile 配置声明 `connect_timeout_seconds: 1.0` 和
  `telemetry_receive_timeout_seconds: 10.0`，但 telemetry 线程构造
  `FrameStreamClient` 时传入的是 10 秒接收超时，后续 `connect()` 也使用
  该值；所以声明的 1 秒 telemetry 建连限制未生效。
- 已验证原因：`FoxyBridgeNode._telemetry_loop()` 没有把
  `self._connect_timeout` 传给 telemetry client，而是只用
  `self._telemetry_receive_timeout`。命令通道另行使用 1 秒值，不能证明
  telemetry 通道生效。
- 修复/预防：为 `FrameStreamClient` 分离 connect 与 receive timeout，
  或者在建连后显式切换 socket timeout；增加可控不响应 endpoint 测试，
  验证建连在声明上限附近返回。
- 证据：
  `integration/lite3_sim_bridge/config/foxy_bridge_upstream_go2_reference.yaml`；
  `integration/lite3_sim_bridge/lite3_sim_bridge/foxy_bridge_node.py`；
  `integration/lite3_sim_bridge/lite3_sim_bridge/transport.py`。
- 后续意义：这是较小的配置语义失真，不否定本次已完成的
  101/101 双云审计，但会使运维人员误判故障切换时间。

### 多个状态入口漂移会让“当前版本”答错

- 现象：canonical ledger 的 `current_working_revision` 和热区均已是
  `office-v2.0.1-go2-geometry-preflight`，但 `AGENTS.md` Current Boundary
  仍写 `office-r2.0.0-preflight`，且父任务 meta 仍保留同一旧 revision。
- 已验证原因：子任务启动新 revision 后，ledger 与 bigmemory 已更新，
  顶层边界文本和父任务元数据没有在同一次状态同步中刷新。
- 修复/预防：明确 revision ledger 为运行版本主键，每次创建/切换
  working revision 时同步检查 `AGENTS.md`、父/子 `task.json` 与热区；
  状态汇报前若值不一致，先报冲突并以 ledger + 实体证据核验，
  不凭单一摘要回答。
- 证据：`AGENTS.md`；
  `.trellis/tasks/08-17-office-crowd-review-visual-r2/task.json`；
  `.trellis/tasks/08-20-v2-0-1-cloud-traversability/task.json`；
  `.pipeline/experiments/2026-08-17_office_l0_scan_crowd/revision_ledger.json`；
  `bigmemory/热区/状态简报.md`。
- 后续意义：归档是验收合约的一部分；顶层边界漂移会直接导致
  对当前版本、已验收范围和下一步授权的错误回答。

### 10 Hz 仿真频率不是墙钟刷新频率

- 现象：`preflight02` 在仿真时间中是 `10.0000002 Hz`，但录制期间
  的墙钟到达率约为 `0.539 Hz`。RViz 的 `Decay Time: 0` 保留
  最近一帧，因此画面可持续可见，但这不代表墙钟每秒收到 10 帧。
- 原因：已确认模拟器 realtime factor 低于 1；本次没有确定其更深层
  的性能瓶颈。
- 修复/预防：汇报点云频率时必须同时列出 sim-time Hz、wall-time Hz
  和 RViz persistence 规则；若验收目标是墙钟实时，必须单独声明并设门。
- 证据：
  `.pipeline/experiments/2026-08-17_office_l0_scan_crowd/results/office_v2_0_1_go2_geometry_preflight02/dual_cloud_scan_audit.jsonl`；
  同目录的 `native_scan_rviz3d_sim_time_metadata.json`；
  `integration/lite3_sim_bridge/config/foxy_native_scan_review.rviz`。
- 后续意义：“点云一直显示”与“点云按墙钟实时刷新”是两个不同合约。
