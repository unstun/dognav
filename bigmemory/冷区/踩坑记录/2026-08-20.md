# 2026-08-20

## v2.0.1 双点云与 Foxy 集成踩坑

### Foxy Python 3.8 会立即求值新增类型注解

- 现象：首次 Foxy 容器测试在导入新双点云代码时失败，而本机新版 Python 没有暴露该问题。
- 已验证原因：Foxy 镜像使用 Python 3.8，模块中的类型注解在定义时立即求值，引用了当时不可解析的类型。
- 修复/预防：在相关模块启用 `from __future__ import annotations`，并把 Foxy Python 3.8 的真实导入/测试作为必要门，不以本机 Python 通过代替。
- 证据：远端 Foxy `test01` 失败和修复后的 build/test 日志；`integration/lite3_sim_bridge/lite3_sim_bridge/run_isaac_v12_fallback.py`。
- 后续意义：ROS 2 Foxy 的 Python ABI/语义是独立兼容边界，不能从 macOS 单元测试外推。

### ROS 2 sensor-data QoS 不匹配会让同帧发布测试收不到点云

- 现象：新 bridge 集成测试虽已发布 raw/planner 两个 topic，订阅端仍未收到消息。
- 已验证原因：测试 subscriber 的默认 reliable QoS 与 `PointCloud2` publisher 使用的 sensor-data best-effort QoS 不兼容。
- 修复/预防：测试 subscriber 显式使用 sensor-data QoS，并同时核对两云时间戳、frame ID 和点数。修复后针对性 Foxy bridge `25` 项测试通过。
- 证据：`integration/lite3_sim_bridge/tests/test_transport.py`；远端 targeted `test03` 失败与 `test04/test06` 通过日志。
- 后续意义：ROS topic 存在或 publisher 已运行不等于订阅合约成立；点云集成测试必须固定 QoS。

### 1 秒墙钟遥测超时会在低实时率渲染中造成重连和审计缺帧

- 现象：`office_v2_0_1_go2_geometry_preflight01` 生成 101 个 sensor scan，Foxy 只审计到 87 个，丢失 14 个 scan ID；同时出现 108 次重连和 14 次 I/O error。
- 已验证原因：原先同一个 1 秒 wall-clock socket timeout 同时承担建连和帧间接收。Isaac 渲染在低 realtime factor 下，相邻仿真扫描的墙钟间隔可超过 1 秒，bridge 因而把正常等待误判为断线。
- 修复/预防：分离建连超时与 `telemetry_receive_timeout_seconds=10.0` 的帧间接收超时。run02 的 101 个 sensor/Foxy 审计全部对齐，scan ID 1--101，重连和 I/O error 均为 0。
- 证据：`integration/lite3_sim_bridge/lite3_sim_bridge/foxy_bridge_node.py`、`integration/lite3_sim_bridge/config/foxy_bridge_upstream_go2_reference.yaml`、run01/run02 的 telemetry 与 scan audit。
- 后续意义：传感器的仿真时间频率不能直接当成 wall-clock socket 超时；低实时率运行必须以 scan ID 端到端审计发现这类隐性丢帧。

### 短预检再次误启完整时长行人门禁

- 现象：`office_v2_0_1_go2_geometry_preflight01` 完成 10.04 秒录制后，被为完整路线定义的行人运动比例门禁拒绝。该失败 run 保留，没有改写为 PASS。
- 已验证原因：新 wrapper 未对 10 秒 short preflight 显式关闭 full-duration terminal/motion gate，重复命中 2026-08-19 已归档的门禁范围问题，并非行人或仿真失效。
- 修复/预防：短预检只记录短窗 motion coherence，完整时长的 terminal/motion gate 明确标为不执行，不改原阈值。新 run ID 的 run02 通过该声明内短回归。
- 证据：run01/run02 结果目录与 `bigmemory/冷区/踩坑记录/2026-08-19.md`中“10 秒视觉预览不能套用完整时长行人比例门”。
- 后续意义：相同的门禁范围坑在新 wrapper/profile 上会重现；每个新运行入口都必须显式绑定 short/full 身份。

### 后处理若导入陈旧 install tree，会按旧 planner-cloud 合约误判新 raw-cloud 运行

- 现象：run02 本体已有 101/101 同帧审计和 251/251 视频可见帧，但首次 `live_pointcloud_continuity_audit.json` 仍要求 `/quad_0/cloud`，因而报 FAIL；一次系统 Python 重试又因缺 `numpy` 失败。
- 已验证原因：外层 wrapper 的 Python 导入路径指向陈旧安装模块，没有加载当前 source tree 中已改为 `/quad_0/cloud_raw` 的 delivery contract。
- 修复/预防：使用已有 `numpy` 的环境并显式把当前 bridge source 置于 `PYTHONPATH`；保留原失败审计和 retry01，retry02 对 `/quad_0/cloud_raw` 的连续性和视频可见性通过，没有重跑仿真。wrapper 也已显式导出当前 source path。
- 证据：`integration/lite3_sim_bridge/lite3_sim_bridge/delivery_reliability.py`、`.pipeline/experiments/2026-08-17_office_l0_scan_crowd/run_remote_office_crowd_native_rviz.sh`、run02 的 `live_pointcloud_continuity_audit*.json` 和 `postprocess_recovery_manifest.json`。
- 后续意义：运行时 source 、ROS install tree 和后处理 Python import 是三个独立同步门；任一陈旧都会生成“数据正确但验证器误拒”。

### Foxy 镜像缺少 torch 使整包测试无法全绿

- 现象：Foxy 中 SCAN 的四个 CTest target 通过，新双点云 bridge 针对性测试也通过，但 bridge 整包收集在既有 `test_mid360_pattern.py` 处失败。
- 已验证原因：钉住的 Foxy 镜像不包含 `torch`，而该既有 MID-360 测试的导入链需要 `torch`；失败不是新双点云断言失败。
- 处置/预防：如实报告“整包未全过”，另行保留 SCAN CTest 和新 bridge targeted 测试的原始结果；未安装新依赖或改写既有测试来隐藏环境缺口。
- 证据：远端 Foxy `test02` 整包日志、`test04/test06` targeted 日志和 SCAN CTest 日志。
- 后续意义：“受影响目标已通过”与“整个 ROS package 全绿”必须分开表述；镜像依赖缺口也必须保留为未关闭验证边界。
